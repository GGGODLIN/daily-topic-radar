# retro 改動有效性：再犯量準、分層驗證、交使用者決定

證據來源：[research.md](/.scratch/retro-change-effectiveness/research.md)。對照論文：[Treude & Baltes, arXiv 2610.34938](https://arxiv.org/pdf/2610.34938)。

## Problem Statement

/retro-workflow 是 Matt Pocock /retro 的跨場版：它把多個 session 反覆出現的問題做成改動（規則、skill、command、hook、script），生效後再記錄同類問題有沒有再犯。2026-11-05 用論文的分類檢查累積庫，發現三個缺口：

1. **再犯紀錄不準。** 觀察的時間欄位常填成紀錄寫入的時間，而不是事件發生的時間。因此改動生效前的事件被記成再犯，有一筆單場報告的限制欄已寫明「早於生效時間」，結果欄仍是 recurrence。另外，cross 階段每個「問題＋改動」組合只留一筆代表觀察，驗收器也只核對組合在不在。例如 2026-11-04 那一輪，搜尋輸出過大這個問題實際再犯 10 次，最後只記 1 次。
2. **分不出改動為什麼沒效。** 15 筆再犯逐筆查原始 session 的結果：9 筆是改動內容沒涵蓋這次的狀況；4 筆是改動已載入也涵蓋了，模型卻沒照做，全是常駐規則、全是 gemini-4-argon；1 筆是改動沒載入；1 筆根本不是有效觀察。現行紀錄分不出這幾種情況，後續修法也就對不準。
3. **沒有判定與撤回出口。** 44 個已生效改動沒有一個被判定有效或無效，因為累積庫的 `effective` 欄位寫死為空值。另外已觀察到兩支 hook 會幫倒忙，但沒有機制把無效或有害的改動送回給使用者決定。

## Solution

1. 再犯紀錄修準：只收生效後、而且當時已載入新版改動的事件；每次事件各記一筆；改判必附理由。
2. 改動有沒有效分三層驗證，並使用當初犯錯的模型：
   - 程式類改動：重跑當初出錯的輸入。
   - 文字規則類改動：回放犯錯的那一刻。
   - 回放做不到時跑整場測試任務；整場也做不到時，才對照過去的紀錄。
3. 常駐規則改完後仍反覆被違反時，把「要不要做成 hook」交給使用者決定。
4. 每個改動都有判定：有效、無效、幫倒忙或證據不足。無效和幫倒忙的進入使用者的待決定清單。

回放工具是全新的東西，第一張工作單先驗證它做不做得到。做不到時，第 2 項的文字規則類改為從整場測試任務開始。

## User Stories

1. 身為使用者，我希望再犯紀錄只收真的在改動生效後發生的事件，生效前的事件與單場報告自己寫明不算的情況不能記成再犯。[user: "a"]（第 1 題選 a：不該算的別算、該算的別漏，兩件都修）
2. 身為使用者，我希望每次再犯各記一筆，不再一輪只留一筆代表，這樣再犯次數才可信。[user: "a"]（同上）
3. 身為使用者，我希望觀察結果被改判時（例如從再犯改成未查），一定附上理由與原始來源，事後追得回。[user: "a"]（第 1 題選 a；「改判附理由」是助理用正式資料確認後提出的修法，使用者沒有糾正）
4. 身為使用者，我希望程式類改動（script、hook）用當初出錯的指令或輸入重跑，驗證擋不擋得住。[user: "a"]（第 2 題改版選 a：分三層）
5. 身為使用者，我希望文字規則類改動用「回放犯錯那一刻」驗證：同一段對話、同一個模型與設定，只把舊規則換成新規則，各回放幾次，看還會不會犯。[user: "話說抓問題是不是還可以對回犯錯的模型，用一樣的配方回放？"]
6. 身為使用者，我希望驗證用的模型是當初犯錯的那一個，不預設用 Opus。[user: "就算跑AI，一定要用OPUS跑嗎？"]
7. 身為使用者，我希望回放做不到時才跑整場測試任務，整場也做不到才退回對照過去紀錄。[user: "b比較好，無法這樣做的時候才用a當fallback"]
8. 身為使用者，我希望每次跑驗證前先看到成本估計，跑不跑由我看了估算再決定；不設自動上限。[user: "1.b"]（YAGNI 審查後的拍板：只顯示估算、不設上限）
9. 身為使用者，我希望常駐規則改完後若仍在 3 場以上不同的 session 被違反，系統把「要不要做成 hook」列給我決定，不自動升級。[user: "A 但要給我決策"]
10. 身為使用者，我希望每個改動都有判定結果（有效、無效、幫倒忙、證據不足），判定時也回放幾個不相關的時刻，檢查新規則會不會讓模型多做事。[user: "a"]（第 4 題選 a）
11. 身為使用者，我希望判成無效或幫倒忙的改動進我的待決定清單，由我決定修改或撤掉。[user: "a"]（同上）
12. 身為使用者，我希望第一批待決定項目就包含已知的四個：瀏覽器規則與搜尋規則要不要做成 hook，以及契約測試自動提醒、pipestatus 連帶擋掉改檔要不要修或撤。[evidence: research.md「第三輪研究」的 hook 副作用表，以及第三題的分模型違反數]
13. 身為使用者，我拒絕某個「做成 hook」或「撤回」的提議後，同一件事不要隔天又出現，除非拒絕之後又累積到門檻。[user: "2.a"]（YAGNI 審查後的拍板：從拒絕時間起重新計算）

## Implementation Decisions

### 名詞與流程

- 現行流程：[evidence: retro-workflow.md:68-99、retro-import.py:375-413、retro-store.py:413-504]
  1. 單場報告：每個 session 一份，由模型讀 session 後寫出，其中「追蹤觀察」記錄已生效改動在這場的表現。
  2. cross 階段：彙整所有單場報告。
  3. 驗收器：session-retro 的 `validate`，檢查每個階段的輸出。
  4. 匯入：retro-import 把 cross 輸出轉成 packet，retro-store 的 `ingest` 寫進累積庫。累積庫是只能追加的 JSONL，問題、決策、改動、觀察都在裡面。
  5. 摘要：retro-store 的 `list --summary`，待決定清單也在這裡。
- 本 spec 新增：事件與載入證據的共用判斷（放在 session-retro）、ingest 寫入觀察、判定紀錄與提議決策紀錄（retro-store）、規則違反查詢（session-audit）、回放工具。[inferred]

### 再犯紀錄

- 事件與觀察分開定義：[evidence: accumulation.md:19 既有「事故的動作位置、優先保留工具 call ID」契約；2026-11-06 架構審查 GPT 席 H1、Opus 席 H2]
  - 事件：一次具體動作。識別鍵優先用工具 call ID，沒有時用 session UUID＋動作所在的原始行號。證據引文另外存，不拿引文行號當事件鍵。
  - 觀察：事件＋改動識別。同一個動作同時違反兩個改動，記兩筆觀察。
  - 同一事件可以追加證據；不同事件不會因為屬於同一條規則就合併。
  - 單場報告的每筆證據標出角色：`action` 是犯錯（或照做）的那個動作，`context` 是佐證，例如事後停掉指令、縮小範圍重查、讀存檔。只有 `action` 產生事件，`context` 存成該事件的補充證據。沒有角色標記的舊報告當舊格式，不算進再犯次數。[user: "照建議"]（2026-11-06 補救動作算不算事件選 a；起因是工作單 10 核對時「搜尋輸出過大」人工拆 22 個事件、程式拆 29 個，多出的 7 個全是補救動作）
- 事件時間由驗收器從原始 session 紀錄產生，不由模型填寫。[evidence: retro-workflow.js:42、session-retro.py:1088-1102]
- 「當時有沒有載入新版」由一支共用判斷讀原始 session 紀錄回答，驗收器、ingest 與回放工具都用它，不各寫一份：[evidence: 2026-11-06 架構審查 Opus 席 H1：10-30 後 909 份主對話中 860 份有 `instructions` 附件，compact 與換模型後會重記]
  - 常駐規則：事件之前最後一次 `instructions` 附件，是否含被改段落的新版原文。
  - skill 或 command：事件之前最後一次 invoke 或重新注入的內容，是否是新版。
  - hook 或 script：事件時間晚於生效時間，就視為磁碟上是新版。
  - 時間順序必須是：生效時間 ≤ 載入時間 ≤ 事件時間。
  - 找不到附件或判斷不出版本時，觀察記為未查並附原因，不收為「已載入新版的再犯」。
- 不收為再犯的情況分兩種，都要留下紀錄：[evidence: research.md obs-23（B 類）；2026-11-06 架構審查 Opus 席 H3、GPT 席 H2]
  - 事件或 session 早於生效時間：記為無效觀察並附理由。
  - 改動已生效但當時沒載入：記為新結果「沒載入」，算在這個改動頭上，因為它代表改動放錯了位置。
- 再犯觀察另記「涵蓋與否」（是／否／不明），這樣「沒載入」「沒涵蓋」「涵蓋了卻沒照做」三類可以直接從資料分出來。[evidence: research.md 第三輪 15 筆分類；2026-11-06 架構審查 Opus 席 H3]
- 舊紀錄的處理：[user: "a"]（舊紀錄選 a）
  - 沒有事件時間的舊觀察標成舊格式，摘要另外列出，不算進再犯次數，也不拿來判定；不得把它們的時間當成事件時間。現有 212 筆舊觀察裡，有 132 筆的時間等於某一輪的截止時間。[evidence: 2026-11-06 架構審查 Opus 席 H9 的 records.jsonl 計數]
  - 舊改動沒有類型與段落錨點，而改動紀錄不能直接補欄位，所以在第一次判定時追加一筆補登紀錄，寫入類型與段落錨點。第一批四個待決定項目都走這條補登路徑。[evidence: retro-store.py:282-298 同 id 不同內容會被拒收]
- 單場報告的追蹤觀察只給事件來源（動作位置＋證據引文）。事件時間由驗收器從原始 session 紀錄產生，不由模型填寫，也不靠讀限制欄的自由文字；這沿用現行流程腳本「時間由下游程式從原文生成」的規定。[evidence: retro-workflow.js:42、session-retro.py:1088-1102；2026-11-06 架構審查 B1]
- cross 階段的契約，從「每組配對保留代表觀察即可」改為：每一筆輸入觀察都要有去向。去向只有四種：[evidence: research.md「第 1 題確認」段：cross 契約原文與 2026-11-03、11-04 的重算結果]
  - 保留。
  - 合併到同一事件，並列出被合併的來源。
  - 改判，附理由。
  - 剔除，附理由。
- 多個分段重複回報同一事件時，依上面的事件鍵合併成一筆，不多算。[evidence: retro-workflow.md:96 既有獨立事件規則]
- 驗收器改為逐筆核對：任何一筆輸入觀察在輸出找不到去向，或改判、剔除時沒有理由，就判不通過。[user: "a"]（第 1 題）
- 改判在累積庫用追加的更正紀錄表達，並連到被取代的那筆觀察，不改寫舊紀錄。ingest 的結果分列新增、重播、補證、更正四種；同一份 packet 重播一次，新增筆數必須是 0。[evidence: retro-store.py:282-298 同 id 不同內容會被拒收；2026-11-06 架構審查 GPT 席 M6]
- 匯入：累積庫的 ingest 直接把 cross 輸出的每筆追蹤觀察寫成觀察紀錄，不再靠 main 逐筆執行 observe；observe 只留給人工補單筆。現況是 ingest 完全不讀 cross 的追蹤觀察，觀察只能手動逐筆建立，逐筆記錄後每輪約 200 筆，手動會在這一步再次挑代表。[evidence: retro-store.py 沒有讀取 `observation_proposals` 的程式（grep 0 筆）、retro-import.py:411-413；2026-11-06 架構審查 B1]

### 分層驗證

- 改動登記生效時，要寫明改動了哪些東西，每項是一組「類型＋位置」：類型是常駐規則、skill、command、hook、script 之一，位置是被改段落的 `{path, line, quote}`，沿用累積庫既有的錨點形狀。一個改動可以同時包含好幾項（例如一條規則加一支 script）。[evidence: research.md 第三輪表 P6「always-on 規則＋script」；2026-11-06 架構審查 Opus 席 M1]
- 重犯條件就是改動紀錄既有的必填欄位 `condition`，不另開欄位；能寫成程式判斷式（例如指令字串比對）的要寫成判斷式。例子：「對 `~/.claude` 根目錄做遞迴 grep 卻沒有排除目錄」。[evidence: retro-store.py:635、:647]
- 判斷有沒有重犯：[evidence: 2026-11-06 架構審查 GPT 席 H4、GPT 新人席 H5、Opus 席驗證設計 ④⑤]
  - 有判斷式就用程式判；沒有判斷式才交給模型判。
  - 模型判斷時看不到哪一組是新規則、哪一組是舊規則。
  - 同時檢查兩件事：目標動作有沒有出現，以及任務有沒有合理往前推進。模型因為停下來不做事而沒出現目標動作，不算有效。
- 第一層，程式類：每個 script 或 hook 的改動，都要把當初出錯的原始輸入加進該工具自己的測試，當成回歸案例。驗證結果作為判定證據，記進累積庫。[user: "a"]（第 2 題改版）
- 第二層，文字規則類，用新的回放工具：[user: "話說抓問題是不是還可以對回犯錯的模型，用一樣的配方回放？"]
  - 輸入：原 session 紀錄、犯錯事件的位置、舊規則文字、新規則文字、回放次數。
  - 做法：工具重建事件之前的對話。系統提示與規則依事件當時的版本重建，只替換目標規則，其餘內容逐字相同。接著呼叫同一個模型產生下一步。
  - 重建方式（2026-11-06 定案）：沿用工作單 01 原型，從 session 紀錄自己組回請求，不啟動 Claude Code。新舊兩組之間只差目標規則段落；跟原請求的差異（01 實測 token 為原請求的 81–95%）逐項列在執行紀錄。忠實度由前置重現檢查把關。[user: "照建議"]（08 重建方式選 a）
  - 輸出：每次回放的下一步原文，以及依重犯條件判斷的結果。
- 回放用的模型、思考深度與路由，沿用原 session 紀錄裡的設定；走中轉站的模型，就走同一個中轉站，不轉送其他服務。[user: "就算跑AI，一定要用OPUS跑嗎？"]
- 回放次數由第一張可行性工作單的結果決定，不先訂固定配額。[inferred]
- 每次驗證保存一份小型執行紀錄：來源指針、規則版本、替換位置、模型設定、每次嘗試與失敗、判斷規則的版本、成本估算。存在不進版控的報告目錄，不另存整段重建的前文。實驗沒有跑完時不產生判定；要接續或換下一層時，先重新顯示成本估算。[evidence: 2026-11-06 架構審查 GPT 席 M7、Opus 席 N1]
- 每次驗證執行前先估算 token 與費用並顯示出來，由使用者決定要不要跑；不設自動上限，也不因成本自動換層。[user: "1.b"]
- 下列情況視為回放做不到，改走第三層：[user: "b比較好，無法這樣做的時候才用a當fallback"]
  - 重建失敗：缺 session 紀錄，或找不到當時的規則版本。
  - 回放用的是原對話紀錄，裡面已經有當時的真人回覆與外部回應，所以「需要真人或外部服務」本身不構成回放做不到。
- 模型或路由已不可用時，第三層同樣要用這個模型，所以直接改走第四層。逾時、中轉站錯誤這類暫時性錯誤先重試，不算做不到。判定紀錄要記下實際走到哪一層，摘要列出「只走到第四層」的改動數。[evidence: 2026-11-06 架構審查 Opus 席 M6、Opus 新人席 M9]
- 第三層，整場測試任務：同一個模型，找或設計一個會重現問題的任務，新舊規則各跑數場，次數由第一張工作單訂。原規則下重現不到問題時，這次驗證不成立，判定記為證據不足；問題需要真人回覆、真實私人資料或外部服務而無法在測試任務重現時，改走第四層。任務的題目不能寫出失敗標籤或預期答案。[user: "b比較好，無法這樣做的時候才用a當fallback"]（整場測試是第 2 題原選項 b；「重現不到判證據不足」與題目限制為推論，後者依 2026-11-06 架構審查 GPT 席驗證設計 ⑦⑧）
- 第三層的副作用檢查：另外找一個這條改動不適用的任務，新舊規則各跑，比較有沒有多出原本沒有的動作或耗時。做不到副作用檢查時，判定要標「副作用未檢查」，摘要不把它當成單純的有效。[evidence: 2026-11-06 架構審查 GPT 新人席 Blocker]
- 第四層，對照過去紀錄：逐一列出這個問題過去的每一次事件，標明改動擋得住哪幾次、擋不住哪幾次。只有前三層都做不到時才用。[user: "b比較好，無法這樣做的時候才用a當fallback"]
- 第一張工作單是回放可行性驗證。[user: "a"]（怎麼動工選 a：「第一張工作單先試回放做不做得到」）
  - 案例一：瀏覽器沿用舊索引，gemini-4-argon。
  - 案例二：根目錄搜尋沒排除目錄，gemini-4-argon。
  - 案例三：一個改動生效前的原始事件，從另一個方向檢查「只換規則」。[evidence: 2026-11-06 架構審查 Opus 席 H8]
  - 通過條件分兩步：先用當時原樣的 context 回放（案例一、二當時已是新規則），要能重現原本的違反，證明重建是忠實的；再量舊規則那一組。[evidence: research.md 第三輪表，案例一、二為改動生效後已載入新規則的 D 類事件]
  - 這張工作單同時訂出回放次數、整場測試次數、判定門檻與判斷規則，訂好後凍結。工作單用過的案例只算校準，正式判定要用沒參與校準的事件；只能用原案例時，結論寫成「原案例回歸」。[evidence: 2026-11-06 架構審查 GPT 席 H4、驗證設計 ⑥]
  - 結果（2026-11-06）：**可行，但有條件，08 要做**。案例一、二原樣 context 重現 2/5、3/5，舊規則組 4/5、4/5；案例三新舊都是 0/5。凍結參數：每個事件先跑原樣 5 次的前置重現檢查，至少 2 次重現才可用；新舊各 10 次；舊規則組至少 4/10 時，新規則組少 4 次以上判有效、最多少 1 次判無效、其餘證據不足；整場測試新舊各 5 場，門檻 3/5、差 3 次。重建出來的請求只有原請求 81–95% 的 token，新舊兩組之間只差規則段落。詳見 [回放可行性報告](/.scratch/retro-change-effectiveness/2026-11-06-replay-feasibility-report.md)。[evidence: 工作單 01 報告]

### 常駐規則被違反時

- session-audit 新增一個只讀查詢：[user: "a"]（檢查入口第 3 項）
  - 輸入：被改段落的位置與原文（同改動紀錄的錨點），以及起始時間。查詢在 session-audit 內部換成它自己的規則身分；累積庫不存 session-audit 的雜湊 id。
  - 時間過濾用每筆違反的事件時間（從來源指針解析），不用 session 開始時間。
  - 回傳：之後違反這一段的不同 session 數、每一筆的來源指針，以及覆蓋量（起始時間後分析了幾場、最近分析到何時），用來分辨「零違反」和「還沒分析到」。
  - 依據：「檔案＋標題」會把同一標題下的好幾條規則混在一起算，例如搜尋規則標題下有 5 條規則、共 36 場，真正的目標段落只有 22 場；session-audit 現存的時間欄位是 session 最早時間。[evidence: session-audit.py:3411-3412、:1672-1696；2026-11-06 架構審查 Opus 席 H4、M7，GPT 席 M5]
- 同一條規則在改動生效後，於 3 個以上不同 session 被違反時，產生一筆「要不要做成 hook」的待決定項；系統不自動建立 hook。[user: "A 但要給我決策"]
- 違反判定來自 session-audit 的免費模型標記，準確度沒有驗證過，所以待決定項要附至少 3 筆原文指針，讓使用者自己判斷。[evidence: session-audit 規則使用量 spec 的 Out of Scope 記載，同類判斷抽查 6/10 正確]
- 使用者拒絕後，以拒絕時間作為上述查詢的新起始時間；之後又累積到門檻，才再次提出。撤回或修改的提議也比照：拒絕後，只有拒絕時間之後的新證據再次判成無效或幫倒忙，才重新列入。[user: "2.a"]
- 第一批：瀏覽器規則（頁面變了要重新讀狀態）與搜尋規則（大目錄要排除）。研究時的分模型場數是檔案層計數，實作後要用段落層級的查詢重算，再送進待決定清單。[evidence: research.md「第三輪補充」：改動生效後 browser-routing 有 Argon 7 場、Opus 2 場違反，code-search 有 Argon 14 場、Opus 14 場違反（檔案層）]
- 規則違反的管道分工：[user: "a"]（規則違反管道選 a：分工）
  - 已經做過改動的規則，也就是改動紀錄裡有這條規則段落錨點的，由累積庫的待決定清單處理。
  - session-audit 把違反寫進摩擦檔之前，先查累積庫的改動錨點清單，遇到這些規則就跳過。這是單向的唯讀查詢，兩邊不需要同步，每條規則只歸一邊管。
  - 其他規則照舊走摩擦檔。已經在摩擦檔的舊條目不搬動。[inferred]
  - 不選「全部走摩擦檔」的原因：摩擦檔待折段有 7,547 條，提議會被淹沒；摩擦檔的休眠協議明文不設數字門檻、不自動重提，跟「拒絕後再累積 3 場才重提」衝突。[evidence: friction/workflow-general.md 各段條目計數；~/.claude/friction/PROTOCOL.md:64]

### 判定與撤回

- 判定流程：[inferred]（2026-11-06 架構審查：規格原本只定義判定紀錄的形狀，沒有產生判定的流程）
  - 觸發：每輪 retro 累積完成後，摘要列出「有新觀察或尚未判定」的改動，以及每個改動的驗證成本估算；使用者選要跑哪些。沒跑過驗證的改動，判定一律是證據不足。
  - 執行與寫入：main 執行驗證（第一層測試、回放工具、整場測試），再用累積庫的新指令追加判定紀錄。判定綁在單一改動上，不綁在問題上。判定紀錄要帶：驗證層級、模型與路由、次數、新舊兩組各自的重犯次數、證據指針、判定者、是否已檢查副作用。
  - 對應規則（數字門檻由第一張工作單訂）：
    - 第二、三層有新舊對照：舊規則組重現達門檻、新規則組明顯下降，判有效；兩組差不多，判無效；舊規則組重現不到，驗證不成立，判證據不足。
    - 第一層：新程式擋住當初的原始輸入，判有效，證據層級標「只涵蓋已知輸入」。
    - 第四層沒有對照組，只能判無效（過去事件都擋不住）或證據不足。
    - 回放不相關時刻時，新規則讓下一步多出原本沒有的動作，判幫倒忙；幫倒忙優先於有效。
    - 判定之後又出現已載入新版的再犯，摘要標「需重判」。
  - 摘要也列出判有效的改動與它的證據層級，不只列無效與幫倒忙。
- 累積庫新增「判定」紀錄，可以對同一個改動記多筆，以最新一筆為準。[user: "a"]（第 4 題）
  - 判定值：有效、無效、幫倒忙、證據不足。
  - 每筆判定附證據指針，可以是重跑結果、回放結果或觀察紀錄。
  - `effective` 欄位改由最新判定產生，不再寫死空值，顯示在每個改動上；問題層級不合併成單一值。一個問題可以有多個改動，例如有一個問題對應三個不同工具的改動。[evidence: retro-store.py:759、:782；2026-11-06 架構審查 Opus 席 M3、GPT 席 H3]
  - 對照：有效對應 true；無效、幫倒忙對應 false；證據不足與尚未驗證對應空值；「需重判」與「副作用未檢查」另外標示，不改變這個值。[inferred]（2026-11-06 架構審查新人席 M6、M11）
- 副作用檢查方式：[user: "a"]（第 4 題）
  - 文字規則類：回放時另外挑幾個不相關的時刻。條件是同一個模型、改動生效後、這個改動不適用的事件點。比較新舊規則下有沒有多做事。
  - hook：從它的觸發紀錄抽樣，判斷是不是擋錯，或連帶擋掉不該擋的動作。
- 判成無效或幫倒忙的改動，以及上一節的「要不要做成 hook」，都出現在累積庫摘要的待決定清單。[user: "a"]（第 4 題）
- 使用者對這些提議的決定，記成新的「提議決策」紀錄，不用既有以問題為單位的決策指令：[evidence: retro-store.py:548-554、:580-585 的決策以問題為單位，改動與進度要求最新決策是批准；2026-11-06 架構審查 Opus 席 H6、GPT 席 H3]
  - 欄位：提議種類（做成 hook、撤回、修改）、對象（改動識別或規則段落錨點）、決定（接受或拒絕）、真人原話的來源指針、決定時間（取自 session 紀錄的時間戳）。
  - 拒絕只影響這一個提議，不會把整個問題的批准狀態翻掉。前面「拒絕後重新計算」的起始時間，就讀這筆紀錄的決定時間。
  - 使用者接受修改或撤回後，實際動手時沿用既有的進度與生效紀錄。
- 第一批：契約測試的 PostToolUse 自動提醒（抽 10 筆全是多餘），以及 pipestatus hook 連帶擋掉同一條指令裡的改檔（44 次裡有 13 次）。這兩個數字來自研究時的單次抽樣，實作後照判定流程重驗再送進清單。[evidence: research.md「hook 副作用」表；2026-11-06 架構審查 GPT 席引證表標為未獨立重驗]

## Testing Decisions

- 好的測試只檢查對外行為：呼叫指令，看輸出和累積庫內容。不檢查內部函式。fixture 和預期結果彼此獨立，沿用 retro-store 測試檔開頭的寫法。
- 要測的入口（已在 2026-11-06 和使用者確認）：
  1. **累積庫指令**：
     - ingest 會把 cross 的每筆追蹤觀察寫成觀察紀錄。
     - 生效前事件記為無效觀察，沒載入新版的事件記為「沒載入」，兩者都不算再犯。
     - 同一事件只算一次；同一動作違反兩個改動時記兩筆。
     - 改判用追加的更正紀錄，沒有理由就拒收；同一 packet 重播新增 0 筆。
     - 判定紀錄的新增，以及每個改動的 `effective` 照對照表產生。
     - 提議決策：拒絕只影響該提議，不改問題的批准狀態；拒絕後不重複提出，直到拒絕時間之後又累積到門檻。
     - 待決定清單列出無效、幫倒忙、達門檻的規則，也列出有效改動與它的證據層級。
     - 舊格式觀察不算進再犯次數與判定，摘要另外列出；舊改動可以追加補登紀錄，補上類型與段落錨點。
     前例：retro-store 的 CLI 測試（`StoreCLI`）。
  2. **回顧流程驗收器**：cross 階段逐筆核對；事件時間與載入判斷由程式從 session 紀錄產生。測試要有一場跨越改動生效時間、中途 compact 的長 session。前例：session-retro 的現有測試。
  3. **session-audit 只讀查詢**：用 fixture 資料庫驗證段落層級的規則對應、以事件時間過濾、不同 session 計數與覆蓋量。fixture 要有一場在拒絕時間之前開始、之後才違規的長 session。另外要驗證：寫進摩擦檔時，已有改動的規則會被跳過，其他規則照常寫入。前例：session-audit 的現有測試檔。
  4. **回放工具**：用假的模型端點回傳預先寫好的下一步。要驗證的事：
     - 新舊兩組之間只有目標規則不同，其餘前文逐字相同；跟原請求的差異逐項列出。
     - 重犯條件判斷正確；模型停下來不做事時不算有效。
     - 缺紀錄、找不到規則版本時回傳「無法回放」加原因；模型或路由不可用時回傳「改走第四層」；逾時與中轉站錯誤先重試。都不會靜默算成有效。
     - 呼叫模型前先輸出成本估算；執行紀錄有來源指針、規則版本、替換位置與每次嘗試。
  5. **retro-workflow 文字契約**：新規定寫進指令說明、流程腳本與累積契約三份文件，測試要檢查三份之間的交接一致，不只檢查關鍵字有沒有出現。前例：retro-workflow 的契約測試。
- 程式類改動的回歸慣例：每個 script 或 hook 改動，都在該工具自己的測試加一筆當初出錯的原始輸入。輸入要先去掉私人資訊，因為 social-info 是公開 repo。例子：pipestatus hook 擋不到 `claude plugin test . 2>&1 | tail -n 35`。[evidence: 2026-11-06 架構審查 Opus 席 M12]
- cross 驗收器與匯入計數的守恆檢查（固定案例）：
  - 斷言：
    - **P1**：每一筆輸入觀察（事件＋改動識別）在輸出恰好有一個去向。
    - **P2**：輸出的結果和輸入不同時（改判或剔除），理由不得為空。
    - **P3**：經 ingest 匯入後，這一批事件在累積庫的最新狀態，等於 cross 輸出中「保留」「合併後」「改判後」的結果，沒有任何一筆靜默消失；同一 packet 重播新增 0 筆。
  - 案例：以 2026-11-03、2026-11-04 兩份真實 cross 報告的結構為藍本，製作去敏後的固定案例。repo 是公開的，不直接放原始報告。
  - 預期值只從固定案例本身重算，不呼叫驗收器的程式碼，也不直接沿用 research.md 的數字。research.md 的 11-04「P6 10 筆」是 10 筆來源觀察，其中有一筆合併了好幾次事件，所以實際有幾次獨立事件，要照事件定義拆分後才知道。[evidence: 2026-11-06 架構審查 GPT 席 H1、驗證設計 ③；Opus 席 M8]
  - 隨機產生輸入、縮小失敗案例的屬性測試延到 v2。[inferred]（YAGNI 審查兩席一致延後）

## Out of Scope

- 自動建立 hook，或自動撤回改動。這兩件事一律交使用者決定。
- 改寫累積庫既有的歷史紀錄，或用新規則重算舊觀察。舊紀錄的處理方式見「再犯紀錄」的舊紀錄條。
- 提高 session-audit 違反判定的準確度。
- 修改 /rules-slim 的瘦身準則。
- 上述第一批四個項目的實際修法。本 spec 只負責把它們送進待決定清單。

## Further Notes

- **數值**：回放次數、整場測試次數、判定門檻由第一張工作單訂；3 場門檻是使用者已定的值，要改需要使用者重新決定。
