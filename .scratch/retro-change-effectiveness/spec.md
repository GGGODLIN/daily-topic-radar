# retro 改動有效性：再犯量準、分層驗證、交使用者決定

證據來源：[research.md](/.scratch/retro-change-effectiveness/research.md)。對照論文：[Treude & Baltes, arXiv 2610.34938](https://arxiv.org/pdf/2610.34938)。

## Problem Statement

/retro-workflow 是 Matt Pocock /retro 的跨場版：它把多個 session 反覆出現的問題做成改動（規則、skill、command、hook、script），生效後再記錄同類問題有沒有再犯。2026-11-05 用論文的分類檢查累積庫，發現三個缺口：

1. **再犯紀錄不準。** 觀察的時間欄位常填成紀錄寫入的時間，而不是事件發生的時間。因此改動生效前的事件被記成再犯，有一筆單場報告的限制欄已寫明「早於生效時間」，結果欄仍是 recurrence。另外，cross 階段每個「問題＋改動」組合只留一筆代表觀察，驗收器也只核對組合在不在。例如 2026-11-04 那一輪，搜尋輸出過大這個問題實際再犯 10 次，最後只記 1 次。
2. **分不出改動為什麼沒效。** 15 筆再犯逐筆查原始 session 的結果：9 筆是改動內容沒涵蓋這次的狀況；4 筆是改動已載入也涵蓋了，模型卻沒照做，全是常駐規則、全是 gemini-4-argon；1 筆是改動沒載入；1 筆根本不是有效觀察。現行紀錄分不出這幾種情況，後續修法也就對不準。
3. **沒有判定與撤回出口。** 44 個已生效改動沒有一個被判定有效或無效，因為累積庫的 `effective` 欄位寫死為空值。另外已觀察到兩支 hook 會幫倒忙，但沒有機制把無效或有害的改動送回給使用者決定。

## Solution

1. 再犯紀錄修準：只收生效後、而且當時已載入新版改動的事件；每次事件各記一筆；改判必附理由。
2. 改動有沒有效分三層驗證，並使用當初犯錯的模型：
   - 程式類改動：重跑當初出錯的輸入。
   - 文字規則類改動：回放犯錯的那一刻。
   - 回放做不到時跑整場測試任務；整場也做不到時，才對照過去的紀錄。
3. 常駐規則改完後仍反覆被違反時，把「要不要做成 hook」交給使用者決定。
4. 每個改動都有判定：有效、無效、幫倒忙或證據不足。無效和幫倒忙的進入使用者的待決定清單。

回放工具是全新的東西，第一張工作單先驗證它做不做得到。做不到時，第 2 項的文字規則類改為從整場測試任務開始。

## User Stories

1. 身為使用者，我希望再犯紀錄只收真的在改動生效後發生的事件，生效前的事件與單場報告自己寫明不算的情況不能記成再犯。[user: "a"]（第 1 題選 a：不該算的別算、該算的別漏，兩件都修）
2. 身為使用者，我希望每次再犯各記一筆，不再一輪只留一筆代表，這樣再犯次數才可信。[user: "a"]（同上）
3. 身為使用者，我希望觀察結果被改判時（例如從再犯改成未查），一定附上理由與原始來源，事後追得回。[user: "a"]（同上）
4. 身為使用者，我希望程式類改動（script、hook）用當初出錯的指令或輸入重跑，驗證擋不擋得住。[user: "a"]（第 2 題改版選 a：分三層）
5. 身為使用者，我希望文字規則類改動用「回放犯錯那一刻」驗證：同一段對話、同一個模型與設定，只把舊規則換成新規則，各回放幾次，看還會不會犯。[user: "話說抓問題是不是還可以對回犯錯的模型，用一樣的配方回放？"]
6. 身為使用者，我希望驗證用的模型是當初犯錯的那一個，不預設用 Opus。[user: "就算跑AI，一定要用OPUS跑嗎？"]
7. 身為使用者，我希望回放做不到時才跑整場測試任務，整場也做不到才退回對照過去紀錄。[user: "b比較好，無法這樣做的時候才用a當fallback"]
8. 身為使用者，我希望每次跑驗證前先看到成本估計，超過上限就不跑、改走下一層。[user: "等等，有這麼多？可以估一下成本嗎"]
9. 身為使用者，我希望常駐規則改完後若仍在 3 場以上不同的 session 被違反，系統把「要不要做成 hook」列給我決定，不自動升級。[user: "A 但要給我決策"]
10. 身為使用者，我希望每個改動都有判定結果（有效、無效、幫倒忙、證據不足），判定時也回放幾個不相關的時刻，檢查新規則會不會讓模型多做事。[user: "a"]（第 4 題選 a）
11. 身為使用者，我希望判成無效或幫倒忙的改動進我的待決定清單，由我決定修改或撤掉。[user: "a"]（同上）
12. 身為使用者，我希望第一批待決定項目就包含已知的四個：瀏覽器規則與搜尋規則要不要做成 hook，以及契約測試自動提醒、pipestatus 連帶擋掉改檔要不要修或撤。[evidence: research.md「第三輪研究」的 hook 副作用表，以及第三題的分模型違反數]
13. 身為使用者，我拒絕某個「做成 hook」或「撤回」的提議後，同一件事不要隔天又出現，除非拒絕之後又累積到門檻。[inferred]

## Implementation Decisions

### 再犯紀錄

- 每筆觀察要帶兩個時間：事件時間，取自原始 session 中該事件的時間戳；載入時間，即新版改動進入模型 context 的時間。兩者都必須晚於改動生效時間，否則累積庫拒收為再犯。現行的時間檢查改用事件時間，不再用紀錄寫入時間。[evidence: research.md 第三輪 A 類（obs-24）與 obs-22／obs-23 拆回單場的結果]
- 載入時間依改動類型決定：[evidence: research.md 第二組分類中 s06、s20 載入舊版、compact 後重新注入新版的觀察]
  - 常駐規則：session 開始時間，或最近一次 compact 重新注入規則的時間。
  - skill 或 command：被 invoke 的時間。
  - hook 或 script：以事件當下磁碟上的版本為準，載入時間等於事件時間。
- 單場報告的追蹤觀察改用結構化欄位記錄事件時間、載入時間、事件來源（session UUID＋原始行號），驗收器據此機械檢查，不靠讀限制欄的自由文字。[inferred]
- cross 階段的契約，從「每組配對保留代表觀察即可」改為：每一筆輸入觀察都要有去向。去向只有四種：[evidence: research.md「第 1 題確認」段：cross 契約原文與 2026-11-03、11-04 的重算結果]
  - 保留。
  - 合併到同一事件，並列出被合併的來源。
  - 改判，附理由。
  - 剔除，附理由。
- 同一事件以原 session UUID＋原事件行號識別。多個分段重複回報同一事件時合併成一筆，不多算。[evidence: retro-workflow 指令既有的「以原 session UUID＋原事件位置識別獨立事件」規則]
- 驗收器改為逐筆核對：任何一筆輸入觀察在輸出找不到去向，或改判、剔除時沒有理由，就判不通過。[user: "a"]（第 1 題）

### 分層驗證

- 改動登記生效時，要寫明改動類型（程式類或文字規則類），以及一個可觀察的重犯條件。重犯條件例如「對 `~/.claude` 根目錄做遞迴 grep 卻沒有排除目錄」。之後每一層的驗證都用這個條件判斷有沒有重犯。[inferred]
- 第一層，程式類：每個 script 或 hook 的改動，都要把當初出錯的原始輸入加進該工具自己的測試，當成回歸案例。驗證結果作為判定證據，記進累積庫。[user: "a"]（第 2 題改版）
- 第二層，文字規則類，用新的回放工具：[user: "話說抓問題是不是還可以對回犯錯的模型，用一樣的配方回放？"]
  - 輸入：原 session 紀錄、犯錯事件的位置、舊規則文字、新規則文字、回放次數。
  - 做法：工具重建事件之前的對話。系統提示與規則依事件當時的版本重建，只替換目標規則，其餘內容逐字相同。接著呼叫同一個模型產生下一步。
  - 輸出：每次回放的下一步原文，以及依重犯條件判斷的結果。
- 回放用的模型、思考深度與路由，沿用原 session 紀錄裡的設定；走中轉站的模型，就走同一個中轉站。[user: "就算跑AI，一定要用OPUS跑嗎？"]
- 回放次數預設新舊規則各 3 次。[inferred]
- 回放只把對話送往原 session 用過的同一個模型路由，不轉送其他服務；回放結果檔只保存下一步原文與判斷，不另存整段重建的前文。[inferred]
- 每次驗證執行前先估算 token 與費用並顯示出來；超過上限就不跑，改走下一層。上限數值在實作前決定。[user: "等等，有這麼多？可以估一下成本嗎"]
- 下列任一情況成立時，視為回放做不到，改走第三層：[user: "b比較好，無法這樣做的時候才用a當fallback"]
  - 重建失敗：缺 session 紀錄、找不到當時的規則版本、模型或路由已不可用。
  - 問題本身需要真人回覆、真實私人資料或外部服務。
  - 成本超過上限。
- 第三層，整場測試任務：同一個模型，找或設計一個會重現問題的任務，新舊規則各跑 3 場。原規則下重現不到問題時，這次驗證判為無效，不算改動有效。[inferred]
- 第四層，對照過去紀錄：逐一列出這個問題過去的每一次事件，標明改動擋得住哪幾次、擋不住哪幾次。只有前三層都做不到時才用。[user: "b比較好，無法這樣做的時候才用a當fallback"]
- 第一張工作單是回放可行性驗證：拿兩個已知案例實際回放，確認重建得出來，而且在舊規則下會重現錯誤。[inferred]
  - 案例一：瀏覽器沿用舊索引，gemini-4-argon。
  - 案例二：根目錄搜尋沒排除目錄，gemini-4-argon。

### 常駐規則被違反時

- session-audit 新增一個只讀查詢：給定規則（檔案＋標題）與起始時間，回傳之後違反這條規則的不同 session 數，以及每一筆的來源指針。[user: "a"]（檢查入口第 3 項）
- 同一條規則在改動生效後，於 3 個以上不同 session 被違反時，產生一筆「要不要做成 hook」的待決定項；系統不自動建立 hook。[user: "A 但要給我決策"]
- 違反判定來自 session-audit 的免費模型標記，準確度沒有驗證過，所以待決定項要附至少 3 筆原文指針，讓使用者自己判斷。[evidence: session-audit 規則使用量 spec 的 Out of Scope 記載，同類判斷抽查 6/10 正確]
- 使用者拒絕後，只有在拒絕時間之後又累積到門檻，才再次提出。[inferred]
- 第一批：瀏覽器規則（頁面變了要重新讀狀態）與搜尋規則（大目錄要排除）。[evidence: research.md 第三題資料：改動生效後 browser-routing 有 Argon 7 場、Opus 2 場違反，code-search 有 Argon 14 場、Opus 14 場違反]

### 判定與撤回

- 累積庫新增「判定」紀錄，可以對同一個改動記多筆，以最新一筆為準。[user: "a"]（第 4 題）
  - 判定值：有效、無效、幫倒忙、證據不足。
  - 每筆判定附證據指針，可以是重跑結果、回放結果或觀察紀錄。
  - `effective` 欄位改由最新判定產生，不再寫死空值。
- 副作用檢查方式：[user: "a"]（第 4 題）
  - 文字規則類：回放時另外挑幾個不相關的時刻。條件是同一個模型、改動生效後、這個改動不適用的事件點。比較新舊規則下有沒有多做事。
  - hook：從它的觸發紀錄抽樣，判斷是不是擋錯，或連帶擋掉不該擋的動作。
- 判成無效或幫倒忙的改動，以及上一節的「要不要做成 hook」，都出現在累積庫摘要的待決定清單。使用者決定修改或撤回後，沿用既有的決策、進度、生效紀錄流程登記。[user: "a"]（第 4 題）
- 第一批：契約測試的 PostToolUse 自動提醒（抽 10 筆全是多餘），以及 pipestatus hook 連帶擋掉同一條指令裡的改檔（44 次裡有 13 次）。[evidence: research.md「hook 副作用」表]

### 流程說明

- retro-workflow 的指令說明與 cross 階段的流程腳本都要改，內容依照上述規則：每筆觀察都有去向、改判附理由、用事件時間與載入時間、寫明改動類型與重犯條件。[inferred]

## Testing Decisions

- 好的測試只檢查對外行為：呼叫指令，看輸出和累積庫內容。不檢查內部函式。fixture 和預期結果彼此獨立，沿用 retro-store 測試檔開頭的寫法。
- 要測的入口（已在 2026-11-06 和使用者確認）：
  1. **累積庫指令**：時間檢查改用事件時間與載入時間，並拒收生效前事件和載入舊版的事件；同一事件只算一次；改判沒有理由就拒收；判定紀錄的新增，以及 `effective` 的產生；待決定清單會列出無效、幫倒忙與達門檻的規則，使用者拒絕後不重複提出。前例：retro-store 的 CLI 測試（`StoreCLI`）。
  2. **回顧流程驗收器**：cross 階段逐筆核對。前例：session-retro 的現有測試。
  3. **session-audit 只讀查詢**：用 fixture 資料庫驗證規則、時間過濾與不同 session 計數。前例：session-audit 的現有測試檔。
  4. **回放工具**：用假的模型端點回傳預先寫好的下一步。要驗證的事：
     - 只有目標規則被替換，其餘前文逐字相同。
     - 重犯條件判斷正確。
     - 缺紀錄、找不到規則版本、模型錯誤、逾時這幾種情況，都回傳明確的「無法回放」加原因，不會靜默算成有效。
     - 成本估計超過上限時不呼叫模型。
  5. **retro-workflow 文字契約**：新規定都寫進指令說明與流程腳本。前例：retro-workflow 的契約測試。
- 程式類改動的回歸慣例：每個 script 或 hook 改動，都在該工具自己的測試加一筆當初出錯的原始輸入。例子：pipestatus hook 擋不到 `claude plugin test . 2>&1 | tail -n 35`。
- 條件式屬性測試（守恆與算帳類，針對 cross 驗收器與匯入計數）：
  - 不變量：
    - **P1**：每一筆輸入觀察（以來源 session、原始行號、改動識別）在輸出恰好有一個去向。
    - **P2**：輸出的結果和輸入不同時（改判或剔除），理由不得為空。
    - **P3**：匯入累積庫後，各種結果的筆數等於輸出中「保留」與「合併後」的對應筆數，沒有任何一筆靜默消失。
  - 適用範圍：隨機產生多份輸入報告，內容包含重複事件、四種結果、合併與改判。
  - 獨立判準：直接從輸入報告重算，不呼叫驗收器本身的程式碼，做法同 research.md 的重算方法。
  - repo 目前沒有 hypothesis 套件。先用標準庫亂數加固定種子產生輸入，失敗時把縮小後的具體輸入存成固定案例。要不要引入 hypothesis，由實作決定。[inferred]

## Out of Scope

- 自動建立 hook，或自動撤回改動。這兩件事一律交使用者決定。
- 改寫累積庫既有的歷史紀錄。舊紀錄的處理方式見 Further Notes。
- 提高 session-audit 違反判定的準確度。
- 修改 /rules-slim 的瘦身準則。
- 上述第一批四個項目的實際修法。本 spec 只負責把它們送進待決定清單。

## Further Notes

- **未決：舊紀錄怎麼處理。** 累積庫只能追加，舊觀察的時間欄位多半是寫入時間。可能的處理方式有三種：全部重算、標成舊格式且不參與判定、保留不動。這需要使用者決定，可以排在實作前的工作單問。
- **未決數值**：成本上限、回放次數、3 場門檻，都可以在實作前調整。
- **成本估計**（2026-11-05，Opus 5.5 官方定價，皆為估計值）：
  - 整場短任務約 2 美元一場。照論文做法每張改動跑 10 場，約 20 美元。
  - 回放每張改動約 2 到 3 美元。
  - gemini-4-argon 走中轉站，費用沒有查。
- **回放的限制**：只測得到犯錯的那一步。模型可能這一步做對了，後面換個地方又犯；新規則讓整條路徑改變的情況也看不到。
- **再犯集中在單一模型**：18 個再犯 session 裡有 16 個是 gemini-4-argon，因此驗證一定要用當初犯錯的模型。
- 研究與討論來源：本 session 2026-11-05 至 2026-11-06 的訪談，四題決定逐題拍板。
