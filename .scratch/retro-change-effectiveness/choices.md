### 資料形狀與格式

**D1 事件鍵與觀察鍵的字串格式**
- 何時：c487263（02；session-retro.py `event_evidence`）
- 決定：要替「一次具體動作」取一個能跨階段比對的名字。現在有工具呼叫 ID 就用它，沒有就用 `<session UUID>:<原始行號>`；觀察鍵是 `<事件鍵>|<改動 id>`。沒選的做法是用雜湊或流水號，那樣人看不懂、也無法從鍵反查原文。
- 規格缺口：規格只說「識別鍵優先用工具 call ID，沒有時用 session UUID＋行號」，沒定字串怎麼拼。
- 影響範圍：cross 去向、ingest 的紀錄 id、補證 id 全都以這個字串為準，之後改格式會讓舊紀錄對不上。
- 判定：sound — 可讀、可反查，和既有 accumulation.md 的「動作位置」契約一致。
- 把握度：高

**D2 cross 逐筆去向的欄位形狀**
- 何時：7ffbe1a（03）
- 決定：cross 要對每筆輸入觀察交代去向。現在用 `tracking_dispositions[]`，每個觀察鍵一項；merged 帶 `merged_into` 與完整 `merged_from:[{unit, issue_id}]`，reclassified 帶 `reason` 與 `to_outcome`，rejected 帶 `reason`。沒選的做法是把去向寫回每筆觀察本身，那樣合併後的來源清單會散落、難以核對「每筆恰好一個去向」。
- 規格缺口：規格列了四種去向，沒定欄位。
- 影響範圍：cross 提示文字、驗收器、retro-import、ingest 都依這個形狀；模型產出要照它寫。
- 判定：sound — 讓 P1「每筆恰好一個去向」能直接機械核對。
- 把握度：中

**D3 累積庫的新紀錄型別**

- 規格缺口：規格要求「改判用追加的更正紀錄」，沒定型別與 id。
- 影響範圍：`list`、摘要、待決定清單都從這些型別重建最新狀態；之後任何新的觀察操作都要沿用。

### API 契約與錯誤行為

**D8 skill／command 從未載入算「沒載入」**
- 何時：c487263（02 Verification Log）
- 決定：事件前完全沒有 invoke 那個 skill 或 command 時，判「沒載入」，不判「未查」。沒選的做法是判未查，那樣「改動放在只有呼叫才載入的地方」這類放錯位置的問題會被藏起來。
- 規格缺口：規格的「未查」寫的是找不到附件或判斷不出版本。
- 影響範圍：「沒載入」計數會算在這個改動頭上。
- 判定：sound — 沒呼叫就是沒載入，可以確定，不是判斷不出。
- 把握度：中

**D9 session 早於生效時間的判法**
- 何時：f54f1d3（04，main 定方向）
- 決定：規格說「事件或 session 早於生效時間記無效」，但累積庫沒有 session 開場時間。現在用 02 的 `load_time`：最後一次載入早於生效時間、之後沒重新載入新版，就判無效並附理由；載入時已生效仍是舊版或從未載入，判沒載入。沒選的做法是另存 session 開場時間。
- 規格缺口：規格沒說「session 早於生效」怎麼判。
- 影響範圍：無效與沒載入的分界。
- 判定：sound — 以實際載入時間判，比開場時間更貼近「當時看到哪一版」。
- 把握度：中

### 並行與效能取捨

**D17 回放呼叫間隔預設 20 秒**
- 何時：6512207（08 Verification Log 第 8 點）
- 決定：回放每次呼叫 Argon 之間要隔多久。現在預設 20 秒（可用 `--gap` 改）；01 關卡跑的是 60 秒，是 main 為了不擠到你同時在用的 Argon 而定的。沒選的做法是沿用 60 秒，一個事件 20 次呼叫要多跑約 13 分鐘。
- 規格缺口：01 沒凍結間隔。
- 影響範圍：正式回放時你前台 Argon 的重試比例。記憶紀錄顯示 Argon 的重試比例跟每分鐘 token 量有關。
- 判定：needs-user — 這是速度與你前台體驗的取捨。暫定做法：維持 20 秒，正式回放時加 `--gap 60`；撤回方式：把 `retro-replay.py` 的 `--gap` 預設改回 60。
- 把握度：低

**D18 副作用檢查每組 5 次**
- 何時：6512207（08 Verification Log 第 7 點）
- 決定：回放不相關時刻做副作用檢查時，新舊各跑幾次。現在預設 5 次（`--runs` 可改）。沒選的做法是跟正式比較一樣 10 次，花費加倍。
- 規格缺口：01 只凍結了正式比較的 10 次，沒凍結副作用檢查。
- 影響範圍：每個改動的回放花費與「幫倒忙」判定的靈敏度。retro-judge 只要新組出現 1 次舊組沒有的動作就判幫倒忙（D22），次數越多越容易抓到。
- 判定：needs-user — 花費與靈敏度的取捨。暫定做法：5 次；撤回方式：跑時帶 `--runs 10`，或改 `retro-replay.py` 預設。
- 把握度：低

**D19 回放成本估算刻意取高**

- 判定：sound — 寧可高估，讓核准有餘裕。
- 把握度：中

**D23 回放只支援常駐規則**

- 判定：sound — 只做 01 驗證過的範圍。

**D24 一次判定只對應一個事件**
- 何時：7b19d0f（07 Verification Log Minor）
- 決定：retro-judge 一次只吃一個事件的新舊兩組；一個改動有好幾個事件時，各事件分別判，累積庫以最新一筆判定為準。沒選的做法是訂一條多事件合併規則（例如多數決）。
- 規格缺口：規格寫了「同一改動多筆判定以最新一筆為準」，沒寫多個事件怎麼合成一個結論。
- 影響範圍：同一改動先後判了不同事件，只有最後一個會顯示。
- 判定：needs-user — 哪個事件的結論代表整個改動是判斷標準問題。暫定做法：每個改動只挑一個沒參與校準的事件判，多事件時人工在判定證據欄註明；撤回方式：之後定合併規則時，在 retro-judge 加多事件輸入並追加一筆判定蓋過去。
- 把握度：低
