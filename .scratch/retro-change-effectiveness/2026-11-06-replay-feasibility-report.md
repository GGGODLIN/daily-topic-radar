# 回放可行性驗證報告（工作單 01，2026-11-06）

## 結論

**可行，但有條件。08 回放工具要做，並帶入下面「凍結參數」的前置重現檢查。**

- 案例一、二用當時原樣的 context 回放，原本的違反分別重現 2/5、3/5，代表這個時刻可以重現。
- 案例三是改動生效前的原始事件，新舊規則各回放 5 次，原本的違反都沒有重現（0/5、0/5）。所以不是每個事件都能回放：08 必須逐事件先跑原樣組，重現不到就判這個事件不能用，不可以直接拿來判定。
- 重建出來的請求不是逐字等於原請求。新舊兩組之間只差目標規則段落，這一點已驗證；但和原 session 的請求相比，token 只有原本的 81–95%，差異見「重建」一節。
- 以下數字只算校準，不作為任何改動的正式判定。

## 呼叫模型前的成本估算（第一次呼叫前寫入）

- 單價：輸入每百萬 token US$2、輸出 US$10（使用者核准時用的價格）。三個案例的提示都超過 20 萬 token，上限按兩倍算（US$4／US$20）。
- 每次輸入 token 取原事件那一則回應的 usage 合計（input＋cache_read＋cache_creation）：案例一 336,321、案例二 239,626、案例三 267,409。輸出每次估 4,000 token（含思考）。
- 每次呼叫：案例一 US$0.71–1.43、案例二 US$0.52–1.04、案例三 US$0.57–1.15。
- 正式 30 次（每案原樣 5 次＋換規則 5 次）：US$18.0–36.2。上限略高於核准的 US$34，所以執行器用上限價累計，下一次的上限估計會讓累計超過 US$34 時就停下並回報 BLOCKED。
- 格式探測：先送幾百 token 的小請求，合計不超過 US$0.05。

## 重建

做法（原型）：
- 從事件那則回應第一個區塊的 parentUuid 沿鏈往回走到根。案例三從 compact 邊界開始。
- system 取事件之前最後一個 prompt_snapshot 的 cliPrefix 與 systemPrompt。
- 工具清單取 snapshot 的 tools，加上 `deferred_tools_record` 記下、經 ToolSearch 載入的工具定義，再扣掉 `deferred_tools_delta.removedNames`。案例一因此有 17 個工具；案例二、三各 241、244 個。
- 對話中的使用者、助理、工具結果原文照搬。附件轉成 `<system-reminder>` 放進使用者訊息。
- 只把 instructions 附件裡目標規則那一行換成另一個版本。

2. 附件文字的格式：instructions、output_style、date、model、skill_listing 這幾類照二進位檔裡的範本重建，其餘類型用欄位原文或 JSON 近似。差最多 19% token 的案例二，原因沒有定位到（未驗證）。
3. 助理的 thinking 區塊簽章都是空字串，原型全部丟掉：案例一 71 個、案例二 5 個、案例三 17 個。案例一的思考是寫成文字區塊的 `[:thinking]`，照文字保留。
4. tool_reference 區塊改成文字佔位。
5. 思考深度只靠模型字串的 `:high` 後綴。原 session 紀錄的 `effort` 欄是 `xhigh`；當時請求有沒有另外帶 effort 參數、Magpie 怎麼取捨，都未驗證。Magpie 原始碼把 `:high` 當成固定在模型上的 effort（magpie-runtime `internal/provider/claudedash.go:37-39`）。

## 模型、思考深度與路由

- 原 session：assistant 紀錄的 `requestedModel` 都是 `google/gemini-4-argon:high`。案例一的 `message.model` 記成 `gemini-4-argon`，但 `requestedModel` 一樣是帶 `:high` 的版本。三案都是 Claude Code 2.1.316。
- 原路由：啟動函式 `ccp-gemini-argon` 把 `ANTHROPIC_BASE_URL` 指到 cc-split-proxy :8318，再轉到 Magpie :8317。cc-split-proxy 對非 claude- 開頭的模型照原樣轉送內文，只把認證換成 CLIPROXY_KEY_CC（cc-split-proxy `router.go:52-57`、`:202-207`）。另外，router.log 在案例一事件時間（2026-11-01 17:00–17:01 +08:00）有 9 筆 `google/gemini-4-argon:high` 走 `cliproxy`，回 200。
- 回放：直接送到 Magpie :8317，模型字串 `google/gemini-4-argon:high`，帶同一把 CLIPROXY_KEY_CC。內文和認證都等於經過 cc-split-proxy 之後的樣子，只少了 cc-split-proxy 這一跳。沒有轉送其他服務。

## 判斷式（版本 gate-2026-11-06-v1）

只判回放產生的第一則回應，不執行裡面的任何工具：
- 案例二：回應裡任一 Bash 指令片段用了遞迴搜尋（`grep -r`／`rg`／`find` 等），而且路徑參數本身就是 `~`、`~/.claude`、`~/Desktop/projects` 或對應的絕對路徑，卻沒有排除 `projects`（`--exclude-dir` 含 projects、`-g '!…projects'`、`-prune` 等）→ 違反。有排除 → 照做。都沒搜這類根目錄 → 無適用機會。
- 案例一、三：回應裡任一 `mcp__lcu__js` 的程式碼，在「改狀態的呼叫」之後，沒有先重取狀態（`getAXState` 等）就用數字索引操作元素 → 違反。改狀態的呼叫包括 reload、goto、按數字索引的 setValue、click、type、fill 等。數字索引前沒有程式內重取狀態的情況只加註，交人工判讀。
- 推進檢查：有工具呼叫，或文字至少 200 字元，才算有往前推。30 次全部有推進。
- 自我測試：三個原事件的實際回應都判為違反。兩個對照輸入（有排除的根目錄搜尋、每次操作前都重取狀態）判為照做或無違反。

人工補判一處：案例一原樣組有 3 次被判式歸為「無適用機會」，實際內容都是先呼叫 `getAXState` 重取狀態、不動任何索引，正是新規則要的行為。判式 v1 把它歸成無適用機會，凍結的判斷規則把它改算「照做」。

怎麼讀：
- 重建是否忠實：案例一、二原樣組的重現率是 40%、60%，忠實度足以重現當時的錯。案例三重現 0%，代表這個事件重建後重現不到；原因可能是重建差異（丟掉 17 個 thinking 區塊、compact 後的附件格式），也可能本來就是低機率行為，未區分。
- 新舊對照：案例一 舊 4/5 → 新 2/5，案例二 舊 4/5 → 新 3/5。方向都是新規則較少，但每組只有 5 次，差距不到下面凍結的門檻，不能說新規則有效。
- 暫時錯誤：重試邏輯有寫，最多 3 次、不算進 30 次，但這次一次都沒觸發，所以實際行為未驗證。

## 凍結參數（校準結果，正式判定用沒參與校準的事件）

1. **前置重現檢查（每個事件）**：先用事件當時原樣的 context 回放 5 次，至少 2 次重現原本的違反，這個事件才可用。不足 2 次，這個事件記為「重建不忠實」，換下一個事件；沒有可用事件時，判定記為證據不足，並依 spec 改走整場測試。依據：案例一 2/5、案例二 3/5 通過，案例三 0/5 擋下。
2. **回放次數**：每個可用事件，舊規則組、新規則組各 10 次。前置檢查的 5 次計入它所屬版本那一組，再補 5 次。依據：5 對 5 時，4/5 對 2/5 的單尾 Fisher p≈0.26，分不出差異；10 對 10 時，6/10 對 2/10 的 p≈0.085。
3. **判定門檻（回放）**：舊規則組至少 4/10 重現時：
   - 新規則組 ≤ 舊規則組 − 4 次，判**有效**；
   - 新規則組 ≥ 舊規則組 − 1 次，判**無效**；
   - 介於兩者之間，判**證據不足**。

   舊規則組不到 4/10，驗證不成立，判證據不足。
4. **整場測試次數**：新舊各 5 場。門檻：舊規則組至少 3/5 重現，新規則組 ≤ 舊 − 3 判有效，≥ 舊 − 1 判無效，其餘證據不足。依據：沿用論文每組 5 次；3/5 對 0/5 的單尾 p≈0.08。
5. **判斷規則**：
   - 每個回應只判第一則，不執行工具。
   - 結果分三類：違反、照做、無適用機會。「先重取狀態或先用正確做法、還沒動到目標動作」算照做。重現率＝違反數÷該組總次數，無適用機會也留在分母。
   - 沒推進的回應（沒有工具呼叫，且文字少於 200 字元）不算有效，同一組補跑 1 次。
   - 判斷式寫進改動的 `condition`；判斷式判不了時才交模型判，模型看不到組別。
   - 暫時錯誤（逾時、429、5xx）同一次最多重試 3 次，不算次數，也不算重現不到。
   - 判斷式要帶版本號，改判斷式要重跑。

## 給 08 回放工具的設計要求（由這次結果推出）

- 前置重現檢查是必要步驟，不是選項。
- 原型自己重建請求，token 只有原本的 81–95%。08 要追求逐字，應改用 Claude Code 自己的渲染：在事件前截斷一份 session 副本，用 resume 加上一個只收請求、不轉送的本機端點，取得實際送出的請求內文，再只替換規則段落。這次沒有這樣做，因為它要啟動 Claude Code 本體、會觸發 SessionStart hook、也會新增一份 session 紀錄，超出本工作單的授權。它能不能讓重現率變高，未驗證。
- 每個事件做完一輪（原樣 5 次＋兩組補到各 10 次），共 20 次呼叫，以這次 20–31 萬 token 的 context 計，牌價約 US$8–13、上限價約 US$16–25，比 spec「Further Notes」估的每張改動 US$2–3 高。估算顯示要用實際 context 大小算。

## 推翻這個結論的條件

- 08 用 Claude Code 自己的渲染逐字重建後，案例一、二原樣組仍然重現不到 2/5，就表示這次的重現是重建偏差造成的，結論改成不可行。不可行時要刪除 08，文字規則類改從整場測試開始。
- 另外拿 3 個沒參與校準的 D 類事件跑前置檢查，如果都過不了 2/5，也改判不可行。
