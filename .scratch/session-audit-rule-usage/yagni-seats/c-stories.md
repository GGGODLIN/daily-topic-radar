# YAGNI 審查（批 C：User Stories ＋ 隱含範圍）

審查範圍：packet 第 20–31 行的 12 條 user story，加 Problem Statement／Solution／Out of Scope／Further Notes 的隱含範圍主張。Implementation Decisions（第 35–46 行）不逐條審；下文提到它們只為標出「這部分屬另一批」。只依 packet 內容判斷，未讀其他檔。

## 1. 一頁最簡版方案

目標只取使用者原話直接要的三件事：(A1) 一份「哪些規則沒遇到場合」的清單、(A2) 用 session-audit 同一引擎、違規算「全域規則摩擦」、(A2/A3) 清單丟進瘦身素材，放在 daily-local 高中低之後的可選欄。

1. **標記**：session-audit 既有的逐段請求裡附上 `~/.claude/CLAUDE.md` 與 `rules/common/*` 全文（第 12 條證據：backpass 讀不到 rules/ 才提重複建議），要模型回每段「有場合的規則 → applied|violated ＋ 引文」；沒場合的不回。不另開模型呼叫。
2. **排除合成對話**：cwd 落在 `/private/var/folders/**`、`/var/folders/**` 的 session 不進統計（第 11 條證據：71/100、584 個目錄）。
3. **規則改版保護（最簡形）**：分段時間早於規則檔最後一次改動時間 → 該段規則標記記「未分析」並寫 limitation。不做 git 版本回溯。這已足以消除第 10 條的那一筆誤判（舊對話被新規則判違規），代價是回填的舊段落少一部分覆蓋。
4. **狀態只存兩樣**：每條規則「最後一次有場合的日期」；每週「成功分析的段落數」（覆蓋）。不存每週 applied／violated／session 三欄表。
5. **零使用清單**：rules-size 週報多一段，列「連續 4 個覆蓋足夠的週都沒場合」的規則（第 7 條：「可以四週」）。daily-local 可選欄多一行「零使用規則 N 條 → /rules-slim」（該欄已存在，A3 註明已實作進 hook 第 12 條）。不改 `/rules-slim` 本身：它本來就讀 rules-size 報告，清單在報告裡就讀得到。
6. **規則摩擦**：violated 的規則，promote 時一條規則一個待折條目（A4「by rule」），未拍板就累加次數與 source_ref；已拍板後再犯開新條目並寫上次處置（A5「正確」）。沿用既有 promote 鎖與 PROTOCOL 權限門（agent-observation、不推薦折入）。
7. **觀察**：登記一筆 trial，+7 看標記與摩擦合併，+30 看第一份清單有沒有出現在可選欄（A6 使用者主動提「分兩段、30 天」）。

這一頁沒有：模型三分類、每週使用量表、git 版本回溯、修改 `/rules-slim` 判斷標準、重開 2026-08-25 的「留」決定。

## 2. 分母檢查

**未定價。** spec 只定價了「瘦身機制沒被用」（digest 提醒 6 次、真人執行 0 次，第 106 行）與「backpass 不準」（6/10、7/10，第 102–103 行），沒有回答「死規則過去造成幾次損失、每次多少」——沒有現行規則總 bytes、沒有每 session 多吃多少 context、沒有一條規則被違反過幾次；而且 Problem Statement／A1 最有說服力的「28 條規則 61 個 session 沒出現」出自被汙染的那一輪（36/61 樣本是 skill-up 假對話，第 101 行），乾淨重跑後的對應數字 packet 沒給。「缺使用量資料所以 /rules-slim 沒人跑」是推論、不是量測：A3 使用者自己說「我懶得做直接關掉也可以」，另一個同樣合理的解釋是瘦身本來就不是優先事項。依 rubric，未定價問題的解法以上面最簡版為上限。

## 4. spec 超出最簡版的部分

1. **第 9 條三分類**（c）— 最簡版只列規則名；人工拍板已是防誤刪的門。
2. **S-1 每週使用量表**（c）— 最簡版只存「最後有場合日期＋每週覆蓋」。
3. **S-5 修改 `/rules-slim`＋重開 2026-08-25 決定**（c）— 最簡版不碰 `/rules-slim`。
4. **第 10 條的機制部分：git 版本回溯**（c，impl 批第 38 行）— 最簡版用「規則改動後的舊段落標未分析」。結果等價，覆蓋少一點。
5. **容量實測票、全文 vs 索引退回**（impl 批第 36–37 行）— 不在本批審，但指出：最簡版同樣要送規則全文，這張票在最簡版裡也存在，不是超出。

受保護但高於「最簡中的最簡」、仍留在最簡版的：第 5 條後半（拍板後再犯開新條目寫上次處置，A5「正確」）、S-3 兩段觀察（A6）。

## 反方證據與推翻條件

- 對整體價值鏈最強的反證：清單唯一消費端 `/rules-slim` 五週內真人 0 次，且使用者在 A3 表明「懶得做直接關掉也可以」。若 +30 天第一份清單出現後使用者仍沒跑過一次 `/rules-slim`，整條零使用管線（第 1、3、7、8、9、S-1、S-5）的價值主張就被證偽，應整體降為 v2 或停。
- 對第 9 條 demote 的推翻條件：第一份清單裡 lint／formatter 類規則占比高（例如超過三分之一）且使用者在 `/rules-slim` 中實際誤判過一條。
- 對 S-1 demote 的推翻條件：使用者或 `/rules-slim` 流程明文需要 applied 次數趨勢（不是只要零／非零）。
- 對 S-5 demote 的推翻條件：使用者跑 `/rules-slim` 時發現現有流程讀不到 rules-size 報告的新段落（這點 packet 沒給證據，我假設它讀得到，依據是第 45 行「daily-local 第 12 條已讀最近一份 rules-size 報告」——這是 daily-local 而非 rules-slim，屬未驗證推測）。
- 對分母「未定價」的推翻條件：補上乾淨樣本的零使用規則數、現行規則總 bytes、每 session 的 context 成本，任一即可把問題定價。
